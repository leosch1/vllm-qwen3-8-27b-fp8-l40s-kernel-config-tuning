Does batch-mix × kernel data predict the actual TPOT?
Corrected version: the first pass at this chart summed one call of each of the 5 shapes per engine step, but the raw per-call histogram (_M_COUNTS) shows the real per-step call counts are 64/48/16/64/64 — matching the served model's actual architecture (64 total layers, 48 linear-attention + 16 full-attention, confirmed against /mnt/models/config.json) — 256 dense-GEMM calls per decode step, not 5. Re-weighted by those multipliers, GEMM goes from ~0.1% of TPOT to a real ~10-20%, and predicted tuned TPOT = actual default TPOT − (predicted default GEMM time − predicted tuned GEMM time) now moves in a comparable range to the actual gap (mean absolute error 2.8ms isolated, 2.6ms contention, vs. actual tuned). It still undershoots the C=1 gap specifically (predicted ~0.3ms drop vs. an actual ~7ms drop) — direct per-call compute savings alone don't explain the very-low-concurrency case, so something beyond raw GEMM time is still at play there.
Prediction error: actual tuned TPOT − predicted tuned TPOT
How far off each prediction is from what actually happened, in ms. Zero = perfect prediction. Negative = the model predicted tuned would be slower than it actually was (under-predicted the win, at low concurrency); positive = the model predicted tuned would be faster than it actually was (missed the loss, at high concurrency). The error crosses zero and grows in the same direction at both ends — the model is systematically too optimistic about tuned at high concurrency and too pessimistic at low concurrency, for both the isolated and contention versions.
