Isolated kernel speedup, default vs. tuned, PER-POINT-RANDOMIZED launch order

A narrower test than the fully-randomized rerun: same 175-point grid, same fixed-tensors-per-point design as this experiment's original (chart.html) — ONE fixed (A,B,As,Bs) tuple per (shape,M) point, reused for every iteration — but at each point, the 4000 launches needed (2000 default + 2000 tuned) are shuffled together and executed in that per-point-local random order, instead of running the full default block then the full tuned block sequentially. No mixing across shapes or M values at all — this isolates whether randomizing just which config runs when, at a single point is enough to remove the original design's bias, or whether the fully-randomized rerun's dramatically different result depended on the broader cross-shape/cross-M mixing too.

Run 1
This reproduces the ORIGINAL result, not the fully-randomized one. Overall mean +21.7%, median +14.9% — not the fully-randomized rerun's +6.5%/+6.7%, and much closer to the original's own headline (+50–70% at small M tapering to single digits). 0/90 anchors negative (matching the original exactly) and 7/85 held-out negative (vs. the original's 6/85 and the fully-randomized rerun's 17/85). So randomizing config order alone, while holding one fixed weight tensor per point, does not reproduce the fully-randomized rerun's flatter, sometimes-negative picture — meaning the earlier "block-order/drift bias" framing was incomplete. What actually changed the answer wasn't which config ran first; it was mixing in many other shapes' and M-values' tensors, which is closer to real serving's cache pressure (many different weight tensors touched between calls to "the same" kernel) than anything a single isolated point, however carefully order-randomized, can produce.
Run 2 — independent repeat, same design, freshly shuffled
Extremely reproducible, and the same conclusion holds. Overall mean +21.7%, median +14.5% — nearly identical to Run 1 (+21.7%/+14.9%). Same anchor-negative count (0/90) and same held-out-negative count (7/85) in both runs. Point-by-point agreement is tight too: gate_up_proj M=1 (+73.4% → +73.0%), M=40 (−7.7% → −7.7%, exact), M=2048 (+2.7% → +2.6%). This design is stable and trustworthy on its own terms — it just answers a narrower question than the fully-randomized rerun, and the two designs' different answers tell us the working-set diversity (not config order) is what was actually driving the original bias away.
