Kernel tuning investigation: Qwen3.8-27B-FP8 on NVIDIA L40S

I made vLLM's kernel config faster.
It made real serving slower.

To improve the performance of Qwen3.8-27B-FP8 running on two NVIDIA L40S GPUs, I ran vLLM's config autotuning script for the block-FP8 GEMM kernel. This resulted in the kernel being up to 62% faster in isolation, and 28% more tok/s for low-concurrency serving. But surprisingly: For high-concurrency serving, the tuned config performed worse than the default. This summary explains how I found the reason for that behaviour (L2 cache assumption) and how the fix made the win hold everywhere.

@leosch1 Qwen/Qwen3.8-27B-FP8 2x NVIDIA L40S, TP=2 vllm/vllm-openai:v0.27.1

1 — Introduction

The warning during vLLM startup

We deploy Qwen/Qwen3.8-27B-FP8 with vLLM, tensor-parallel across two NVIDIA L40S GPUs. At startup, for every distinct weight-matrix shape in the model, vLLM logs this once:

WARNING [fp8_utils.py:851] Using default W8A8 Block FP8 kernel config.
Performance might be sub-optimal!
Config file not found at .../configs/N=17408,K=5120,device_name=NVIDIA_L40S,dtype=fp8_w8a8,block_shape=[128,128].json

vLLM wasn't able to find a custom config for the necessary weight matrix shape and GPU combination, so it uses a default config, which might result in sub-optimal performance.

That warning is the hook for this whole investigation, so let's try to understand it.

What's actually being warned about

Every forward pass in an LLM involves normalisations, activation functions, softmax etc. but the majority of the computation is matrix multiplication. In particular, the model's linear projections are GEMMs (General Matrix Multiply): A[M,K] @ B[K,N] = C[M,N]. A is the activations and B is the weight matrix. M are the number of rows, one per token currently being processed. K and N are the input and output dimensions. As an example, if A ∈ ℝ2×3 and B ∈ ℝ3×2, then C ∈ ℝ2×2:

A · B = C. Here, M=2 tokens, K=3 input features, N=2 output features.

For our model, the GEMM operation is implemented in _w8a8_triton_block_scaled_mm. Depending on which of the model's weight matrices is being multiplied, the shape of B differs. In total, the GEMM operation is used with five different weight matrix shapes:

  • in_proj_qkvz N=8192, K=5120
  • out_proj N=5120, K=3072
  • gate_up_proj N=17408, K=5120
  • down_proj N=5120, K=8704
  • qkv_proj N=7168, K=5120

As you can see above, the five weight matrix shapes are distributed across different model layers. Using NVIDIA Nsight Systems we can inspect the actual kernel calls. We can see that there are other kernels (GPU functions) launched, but around 80% of kernel execution time is used by the _w8a8_triton_block_scaled_mm kernel:

The _w8a8_triton_block_scaled_mm kernel is written in Triton, a language for writing GPU kernels at a higher level than CUDA. This Triton kernel exposes several launch parameters that change how fast it runs, with no single value that's best everywhere. The right choice depends on the operand's matrix shapes and the exact GPU. When there is no custom config setting the launch parameters, vLLM uses the following fallback and triggers a warning.

{
    "BLOCK_SIZE_M": 64,
    "BLOCK_SIZE_N": 128,
    "BLOCK_SIZE_K": 128,
    "GROUP_SIZE_M": 32,
    "num_warps": 4,
    "num_stages": 2
}

Briefly, what each of these actually does: BLOCK_SIZE_M/N define the output tile size, while BLOCK_SIZE_K determines the chunk size processed per iteration. num_warps defines how many groups of 32 threads work on each tile concurrently. num_stages defines how many pipeline stages overlap memory loads with compute. GROUP_SIZE_M is to influence the order in which output tiles are scheduled.
If you want to understand CUDA concepts such as threads and blocks, I can recommend this video as an introduction.

For some combinations of weight matrix shapes and GPUs, vLLM ships with custom config files which contain an optimised selection of thse parameters. On startup, vLLM checks if it can find such a custom config file in this folder. For the weight matrix shape + GPU combination we are using, there is no such config file - thus the warning at startup.

In order to add optimised configs for new model + GPU combinations, vLLM ships an autotuning script (benchmark_w8a8_block_fp8.py) that grid-searches different combinations of the launch parameters and keeps the fastest. I ran it for the 5 shapes used by Qwen3.8-27B-FP8 (TP=2) resulting in a config file per shape. The JSON file is keyed by the batch size. (1, 2, 4, etc.) vLLM chooses the closest match for a given batch size and uses the corresponding parameters to launch the GEMM kernel.

The next question after getting the custom configs from the autotuning script is: Did the performance improve?

2 — Tuned results

Yes, but...

Let's compare the kernel-level performance of using the default config vs. using the tuned config. Running the same performance test used by the autotuning script and averaging across weight matrix shapes gives us the following result:

Mean kernel-level speedup compared to default config

Higher is better. Filled = exact tuned batch size matched. Ring = using nearest batch-size.

A big improvement for small batch sizes: Roughly 62% at the smallest batch sizes, meaning that the kernel takes 38% of the time it would need using the default config. As the batch size grows, the performance improvement gets smaller (but importantly never significantly negative). A probable explanation for the smaller improvement for bigger batch sizes is the BLOCK_SIZE_M parameter. The default config sets it to 64, no matter the batch size. For a batch size of M=1 this leads to 63/64 rows of tiles to be wasted, but the wasted amount is lower for bigger batch sizes. The tuned config sets the BLOCK_SIZE_M closer to the actual batch size:

  • M=1 → BLOCK_SIZE_M=16
  • M=32 → BLOCK_SIZE_M=32
  • M=64 → BLOCK_SIZE_M=64
  • M=128 → BLOCK_SIZE_M=128
  • M=4096 → BLOCK_SIZE_M=128

This is a clean, unambiguous, textbook autotuning result.

Now, instead of kernel-level performance, let's look at the performance improvement for actual model serving using vLLM's vllm bench serve command, sweeping --max-concurrency from 1 to 128:

Output tok/s increase using tuned config

Higher is better. End-to-end performance at different amounts of simultaneous requests.

For end-to-end serving performance, we also see a big improvement for low concurrency which gets less, as the number of simultaneous requests increases. That is exactly what the kernel-level chart above already predicted.

But: For more than 48 simultaneous requests, using the tuned config is actually worse than using the default config. How can that be? Nothing in the isolated measurement ever showed a significant negative improvement for the tuned config.

How can a kernel config that's faster across the whole batch-size range make the e2e system slower under high-concurrency load?

That's the question the rest of this post answers.

3 — Narrowing the target

What is responsible for the performance degradation?

Using GPU hardware-counter traces (nsys, injected directly into the live serving process) we can see every GEMM launch's duration. After mapping the launches to the 5 weight matrix shapes, we can plot their durations on a histogram. We want to compare the resulting duration distributions of the default and tuned configs. We do that for both the low concurrency scenario (1 simultaneous request) and the high concurrency scenario (64 simultaneous requests).

Now, what about the high concurrency scenario?

How are launch durations distributed for default config and tuned config? The more left, the better.

Most of the distribution still slightly shifts left. BUT: One of the launch cluster shifts right very strongly. (Keep in mind that the x-axis is logarithmic) gate_up_proj launches at batch sizes around M=2000, almost double in duration from ~1100ms to ~2000ms. For other shapes and batch sizes the tuned config generally is faster. So we have one GEMM shape (M≈2000, N=17408, K=5120) which is entirely responsible for erasing the tuned config's benefit at high concurrency.

But in the isolated kernel benchmark had shown a performance improvement around that shape using the tuned config (+7.9% speedup at M=2048, N=17408, K=5120) So: why does the tuned config win in the isolated benchmark at that shape and lose badly in real serving?

4 — The mechanism

Isolated benchmark and real serving aren't measuring the same thing

If it isn't GEMM shape, something about the two measurement regimes themselves must differ. Looking again at the nsys trace file, we can find out how busy the compute units are (Tensor Active) vs. how saturated the memory bus is (DRAM Read). For the specific shape's kernel launches,these are the averages in both isolated and real serving benchmarks:

BenchmarkTensor ActiveDRAM Read
Isolated58.2%14.9%
Real serving28.3%72.8%

We can see that in the real serving benchmark DRAM Read jumps to 72.8% (of the L40S' 864 GB/s max theoretical bandwidth). At the same time the proportion of active tensors halves (58.2% → 28.3%) — this is a textbook example of memory access becoming the limiting factor.

So: why would the exact same kernel, computing the exact same matrix multiply, need to pull far more data from DRAM under real serving than it does in isolation?

The autotuning script's hidden assumption

The answer is sitting in the autotuning script's code. For a fixed batch size M, it allocates one input pair: One activation tensor A and one weight tensor B. It then reuses that exact same pair across all 1,280 candidate configs:

A, As = make_A(M, K)
B, Bs = make_B(N, K)          # allocated ONCE
for config in search_space:
    t = benchmark_config(A, B, As, Bs, config)   # every launch reuses the SAME B

That is not inherently wrong. But to know if it makes sense for what we are trying to measure, we have to understand the GPU's caching behaviour.

The GPU's L2 cache (96 MiB for L40S) holds recently accessed memory. If the same tensor is read more than once, it gets retrieved from L2 cache given it is still there. So in the autotuning script, when benchmarking all the different combinations of kernel parameters, the matrix multiplication operands A (10 MiB) and B (85 MiB) can always be retrieved from the L2 cache. (Probably not all of it considering other things like the result matrix need to fit in L2 cache too, but a big part A and B stays cached.)

For real inference, that isn't the case. During a forward pass, the GEMM kernel gets launched at many layers, and each GEMM operates on a different activation (A) and weight matrix (B). The same weight matrix is reused at the same layer in the next forward pass, but at that point 255 other GEMM operations (and other things) used the L2 cache and the same weight matrix has long been flushed out. That is why in real inferencing, the GEMM operands always need to be fully fetched from memory.

The autotuner measures a GEMM whose operands are cached. Real serving never lets the operands stay in cache.

That's the gap. The autotuner script and isolated benchmark are assuming a memory-locality condition that real serving never actually provides.

5 — The specific parameter

Which parameter is most affected?

So given that our scenario during tuning and real inferencing are not matching; can we point to the paramater on which this has the most "bad influence"? In other words, which of the tuned parameters is most sensitive to this mismatch and would changing it by hand fix the high-concurrency performance degredation?

A likely candidate for that is the parameter that controls the order in which output tiles are scheduled: GROUP_SIZE_M. According to the official Triton Matrix Multiplication Tutorial, that parameter "affects the L2 cache hit rate". If you're interested, check out the full explanation TODO I wrote on how the current autotuning script leads to a suboptimal choice for GROUP_SIZE_M.

Testing the hypothesis with the narrowest possible patch

Let's test how much of the performance degradation we can make up for by manually changing gate_up_proj's GROUP_SIZE_M parameter for batch size M=2048 from 1 to 16. At this specific batch size, this essentially changes the order in which the kernel works through the tiles from row-first to column-first. Every other parameter and every other shape and batch size, we leave exactly as the autotuning script produced it.

GEMM launch durations, 64 simultaneous requests

The first two histograms we already know. Does the manual fix undo the deterioration?

Yes, it worked! The culprit of the performance degredation (gate_up_proj at M≈2000) moved back left and is now at a similar place as in the default config's histogram. This movement of that cluster from 1961µs to 1063µs results in the overall mean dropping with it and the tuned config now being faster than the default config even at high concurrency (c=64).

6 — Fixing the root cause

Patch the assumption, not just the config

The single-parameter patch treats the symptom. The actual defect is in the autotuning script itself: it let's the GEMM's operands be retrieved from L2 cache, which isn't the case during real serving.

To fix this, we can simply modify the autotuning scipt to flush the GPU's entire L2 cache before every candidate measurement.

l2 = torch.cuda.get_device_properties(device).L2_cache_size
flush_buf = torch.empty(int(l2 * 1.5) // 4, dtype=torch.int32, device="cuda")

def benchmark_config(...):
    for _ in range(num_iters):
        flush_buf.zero_()            # the fix: evict L2 before every launch
        start_event.record()
        run()
        end_event.record()

Before creating a new set of configs using the modified autotuning script, we can actually use the same flush mechanism to benchmark our existing unpatched tuned config in the cold cache scenario (which is closer to real inferencing than the warm cache scenario we used before).

Using the original autotuner's warm-cache assumption, the kernel-level benchmark didn't show any performance degredation for gate_up_proj at M≈2000. How does it look like using the cold-cache assumption?

Now we can finally see on an kernel-level benchmark, how gate_up_proj is performing worse using the tuned config for certain batch sizes, including at M≈2000 (which was the batch size often used for concurrency=64).

Other GEMM shapes aren't affected because their weight matrices are far smaller. Smaller weight matrices mean everything can comfortably stay in L2 cache without needing to take turns with other competing cache content, and thus the tile scheduling order (GROUP_SIZE_M) is essentially irrelevant for them.

7 — Summary and next steps

Learnings and next steps

Summarised

startup warning: no tuned config→ ran vLLM's autotuner→ faster in isolation and at low concurrency→ slower at high concurrency→ traced to gate_up_proj at M≈2000→ GROUP_SIZE_M=1 is the problem, picked under a warm cache→ flush L2 while tuning→ faster at all concurrencies

Learnings

  • An optimiser optimises for the conditions it creates. The autotuner's measurements were correct for the assumptions it took. Optimising for real serving (e.g. using vllm bench serve) instead of kernel-level performance would be great, but much more time-consuming. When running in production, we must specifically optimise for the actual usage patterns. That is nothing a generic autotuning script can do.
  • "Fits in cache" is not "stays in cache." An 85 MiB weight matrix against a 96 MiB L2 looks safe on paper. It isn't: at that occupancy the output writes and the cache's set-associativity still lead to cache eviction.
  • AI collapsed the cost of the experiments, not the need for judgement. Thanks to AI, going from a question to data took minutes rather than days, which is why I was able to run more than 30 experiments for this. But wrong interpretations occur surprisingly often and the turns that mattered were mostly human ones.

Next steps

There is currently no shipped tuned config in vLLM's own vllm/model_executor/layers/quantization/utils/configs/ directory for this exact GPU/model/tensor-parallel-degree combination. In order for others to be able to use my work as well, I:

  • Shipped the L2-flush-tuned config as a PR to vLLM's configs directory.
  • Still want to raise the L2-flush fix with the vLLM community as a change to the autotuning script itself, not just this one deployment's config. The directory ships 219 tuned configs across 12 GPU types, presumably all using the always-warm search loop. Configs for weight matrices approaching the GPU's L2 cache size are potentially exposed to the same regression traced here.
