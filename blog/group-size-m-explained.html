The GROUP_SIZE_M Mystery

A companion to the main blog post. This tries to reproduce the unexpected behaviour that the vLLM kernel config autotuner chooses row-major tile schedule ordering (GROUP_SIZE_M=1) instead of column-wise grouping when the GPU's L2 cache isn't flushed between consecutive kernel launches.

What GROUP_SIZE_M is for

The GEMM kernel analysed in the main blog article multiplies two matrices, A and B, into a third matrix C. The computation is split into tiles and the parameter GROUP_SIZE_M influences the order in which the tiles are scheduled. By grouping the output tiles into stripes of height M, we can tell the kernel to first schedule the tiles inside that group (top-to-bottom), before going to the next group. Setting GROUP_SIZE_M=1 essentially means, that the height of the group is 1, resulting in the whole output matrix tiles being scheduled in a row by row order (row-major). For the other extreme, if we set GROUP_SIZE_M to the number of total tiles vertically, the whole output matrix tiles will be scheduled in a column by column order (column-major).

Order matters because each tile reads a chunk of A and B, and based on how recent a chunk was used, it might still sit in L2 cache or might already have been evicted. The goal of GROUP_SIZE_M is trying to increase the number of elements which can be retrieved from the fast L2 cache (and reduce the calls to the much slower DRAM).

Triton's matrix multiplication tutorial shows a concrete example: computing the first 9 output tiles of a 9x9 tile grid. Row-major sweeps them as a thin 1x9 strip — one row of A, but a different column of B for every tile, so all 9 B columns get loaded: 90 blocks total. Setting GROUP_SIZE_M=3 would allow us to calculate the first 9 tiles with only 54 blocks needed thanks to more reuse. If the L2 cache happens to be smaller than what's needed for 90 blocks, this would result in the second strategy finishing faster than the first.

In practice

With an empty L2 cache, this holds up in practice: grouped beats row-major, as expected. But vLLM's autotuner times candidates back-to-back without clearing the cache, so later ones run warm — and under that condition, row-major won instead.

Reproduce the unexpected result

To reproduce this in an easier to understand setting, I shrunk the size of A, B, C, and the cache down. A is a 3x2 matrix, B is a 2x5 matrix and the cache can store 13 elements at once. To further reduce the complexity, this example doesn't use any tiling. (BLOCK_SIZE_M=1, BLOCK_SIZE_N=1, BLOCK_SIZE_K=2).

The two scenarios we want to compare are the two extremes GROUP_SIZE_M=1 (row-major) and GROUP_SIZE_M=3 (column-major).

Honestly, I can't fully explain why

I can't yet give a clear explanation of why and under exactly what circumstances this effect happens but it seems to depend on:

  • How much smaller the cache is than everything moving through it in one pass.
  • The specific way DRAM addresses map onto cache slots. (Simple LRU doesn't work)
  • How and when the cache evicts things, not just its capacity.
  • The dimensions of A and B.

If you have a intuitive way to explain this behaviour, please let me know.
